# Fidenne Privacy

This document states **what Fidenne keeps on your device, what it sends off your device, and what it does not collect at all**.
The basis for every statement is the app's source code, and each section names the automated check that verifies that promise on every build.

Reference version: source <!-- gen:version -->0.5.0<!-- /gen --> · last verified 2026-09-18

---

## 1. Audio — it is neither kept on the device nor sent off it

**Fidenne does not store the audio it captures or converts.** Samples flow only through memory, from capture through the resampler and modulator to the output device. There are no files on that path. There is no recording feature and no "save the current song" feature.

- In the engine code (`src/`, `include/`), there are **no calls that open a file or write bytes other than five recorded exceptions.**
  The exceptions are the coefficient cache, the library index, and the output-rate restore record (writes; none handle sample formats), plus two reads of files the user picked (no write API),
  and the check verifies the conditions of each exception.
- The C ABI does not hand the app any sample buffers. Only numbers and state snapshots pass through. **The app cannot see audio.**
- There is no path that sends audio over the network either. There is no streaming, upload, or cloud backup feature.

This promise is checked automatically on every build.

These checks are static checks that scan the source, so they do not directly measure behavior while the app is running (§5).

## 2. What stays on the device

Everything is a local file, and none of it is sent anywhere. The location is `~/Library/Application Support/Fidenne/`
(the `…/Aural/` folder used by earlier versions is moved to this name as-is the first time a new version runs),
and the files the app creates are stored so that only the owner can read and write them (`0o600`).

Checked automatically on every build: that exported bundles have no device UID and that the salt differs per run, and that **distribution bundles have no device hash**;
listening history 0600 · rotation · no local file paths; lyrics cache 0600 and no song names in file names; library index and its journal · output restore record ·
music links 0600; and the behavior of the diagnostic tools. Distribution builds go through one more check of the distribution bundle after the build.

Even when developers run the checks, the files, settings, and Keychain items above do not change — checks that use app code write only to their own temporary folder and temporary settings,
and the before and after of the check suite are compared automatically (values as hashes only).

**Apple Music rate detection reads Music's lines in the macOS unified log.** While the app is open it runs `log stream` and, from the decoder lines that the Music process (subsystem `com.apple.coreaudio`) writes while playing an Apple Music song, reads that song's sample rate and format. The lines themselves are not written anywhere and not sent — only the numbers taken from them (rate · bit depth · channels) remain, in the track rate memory and the listening history's sound information above; developer builds also write the same numbers as one line of the playback log. If the account is not an administrator, macOS refuses `log stream` and this detection is off.

**Developer (PERSONAL) builds collect more.** An app built with `AURAL_DIAGNOSTICS_TIER=PERSONAL` additionally collects system and CoreAudio context at launch. The distribution default is `DISTRIBUTION`, and a post-build check verifies that boundary. Which tier you have is shown next to the app name as `개발자용` (developer) / `배포판` (distribution).

**Receiving side.** `127.0.0.1` — a loopback listener (port 53682) that receives the Spotify sign-in callback in the browser. It is open only while the user is starting the Spotify connection, and it closes when done. What goes out: nothing — it does not leave the device.

**Receiving side.** `fidenne-browser-bridge/bridge.sock` — a Unix socket (in the user's temporary folder, readable and writable only by the owner) that receives from the Fidenne extension in Chrome · Edge the YouTube Music song information (title · artist · album · duration · position · album art URL · playlist ID · page volume and mute · codec · liked status) and the queue (title · artist · duration · video ID for up to the next 50 songs), the songs of a playlist screen the user opened (video ID · title · artist · duration for up to 500 songs per list, and the list name), the library screens the user opened (playlists · albums · artists — ID · name · subtitle for up to 500 items per screen), and album art (JPEG · PNG of 512 KB or less), and that returns playback controls and requests to open library screens. The extension, helper, and app exchange only a fixed set of commands (playback controls, queue, opening a screen, search, menu lists). It is open only while "Connect with Chrome · Edge extension" (Chrome · Edge 확장과 연결) in Settings › Privacy › YouTube Music is on (off by default), and when turned off it closes and also deletes the Chrome · Edge connection files (NativeMessagingHosts). What goes out: nothing — it does not leave the device. Received song information stays only in the song identity DB (songs played continuously for 5 seconds), opened playlists in `youtube-music-browser-playlists-v1.json`, opened library screens in `youtube-music-browser-library-v1.json`, and album art only in memory. The app makes no request to the art address — the art is what the extension read, inside the browser, from that address on the two image servers the page uses (`lh3.googleusercontent.com` · `i.ytimg.com`), without cookies and preferring the browser cache, and then shrank (if it is not in the cache, the browser makes one request to that server — a place where the page already receives the same image).

**Per-item switches.** Each destination can be turned off and on separately, and they are asked about together on one screen the first time you run the app. If destinations are added later, the same screen appears once more, showing only the added lines. Even with everything off, capture, DSP, DSD conversion, DAC output, and local playback continue as before — only the integration features that use that destination are turned off.

**Diagnostic bundles are not in this table.** That is because the app does not send them. "Send by mail" (메일로 보내기) only opens the mail app with the address, a subject and questions filled in, and attaches nothing; the bundle goes by mail, not into a public issue. "Open GitHub issue
composer" (GitHub 이슈 작성 창 열기) opens the new-post screen in the default browser and pre-fills only the title, app version, macOS, and model. Attaching a bundle file and posting it is entirely the user's own action, and there is no code path in the app that sends a bundle (an automatic check confirms this). That is also why `github.com` is in the registry's `browserLinkHosts` — the issue composer is not a place the app sends requests to but an address handed to the browser. The reason `github.com` is also in the table above is
the "Check for Updates…" (업데이트 확인…) alone (see below).

**How a report you send is handled.**
1. A report sent by mail reaches only the developer. It is never published and never put in the source repository.
2. Before analysis, the sender's name, mail address and signature are removed. The remaining report and bundle (which holds the titles, artists and services of the songs played in that period) may be read with analysis tools, including an AI tool (Anthropic's Claude).
3. The bundle is deleted within 90 days after the problem is closed. The mail itself stays in the mailbox so replies are possible.
4. To have a report deleted earlier, write to us at: fidenne.support@gmail.com

- **The update check asks only once, only when you press it**. When you press "Check for Updates…" (업데이트 확인…) directly below "About Fidenne" (Fidenne 에 관하여) in the app menu and at the very top of the Settings window, it reads one file, `appcast.xml`, attached to the latest release of the public repository, from `github.com`. GitHub redirects that request to its attachment server `release-assets.githubusercontent.com`, so two places are in the table, and the switch is one. What goes out is only a User-Agent containing the app version (`Fidenne/<version> (build <number>)`) and the IP address; no cookies, songs, devices, or settings are carried (an automatic check confirms this). The app never checks on its own, and never downloads and installs — if there is a new version, it copies the command for you if you installed with Homebrew, and opens the release page in the browser if you installed with the .dmg. The developer does not receive this request. GitHub shows the repository owner the **number** of attachment downloads, but the IP is seen only by GitHub. In builds from before the public account was decided, there is no address to check, so the menu item is disabled and there is no request.
- **An address a server redirects to must also be in the table to be followed**. The transport layer used to check only the address of the first request against the table, and if a server named another address with a 3xx it followed it as-is. Now it applies the same check to every redirected address — it must be a place in the table, its switch must be on, and it must not redirect to the app's receiving side (the loopback listener). Otherwise it does not follow, and ends that request as a refusal (an automatic check confirms this).


- **Lyrics search sends nothing before consent**. The first time it becomes necessary, a sheet stating what is sent is shown once, and if you decline, only local `.lrc` files you connected yourself are used. There is a toggle in the display settings. The consent check is not at the place that builds the request but in **the transport layer itself**, so it cannot be bypassed even if one more caller appears, and an automatic check verifies that zero requests go out before consent and that only four fields go out after consent.
- **The song currently playing is looked up ahead of time**. Only when there is consent and the source is not blocked, it looks up once **after the same song has kept playing for 5 seconds or more**. If you skip through songs quickly, no requests go out for the songs passed — only the one song you are listening to is looked up. The consent gate, the per-song memory, and the block pause pass through **the same ones** as when you open the panel directly.
- **Local files are looked up under the same rules**. Files played from the Fidenne library also have lyrics looked up when the song changes and at the 5-second lookahead. What goes out is only the four items from the file tags — title · artist · album · duration — and the file path, file name, file contents, and the app's internal song identifier are not carried in the request (an automatic check confirms this). The consent gate and block latch are the same as for streamed songs.
- **A server that refused is not asked for a while**. If `lrclib.net` answers 429, lyrics lookups for all songs stop for the time the server wrote back (if none, 10 minutes, clamped between 1 minute and 1 hour); on 401 · 403, they stop for 1 hour — during that time not a single request goes out and even Refresh cannot lift it. Turning lyrics search off and on in the settings lifts it immediately. Previously a single refusal lasted until the app was restarted, so once blocked, the lyrics of every song disappeared for that whole run.
- **At most three requests per song**. If the exact lookup (title · artist · album · duration) does not find it, it searches by title · artist, and if it is still not found it searches once more by **title only** — the last request carries nothing but the title. Even if the server answers 503 (busy), it moves on to the next request, and if there is no response at all (connection · timeout) it stops there. A song that has already been answered is not automatically asked again — "not found" uses that answer for 30 minutes and "lookup failed" for 2 minutes, and after that it asks again when you play that song again or open the panel. Refresh asks once more at any time. The User-Agent sent is `Fidenne/…` and does not imitate another browser. This rule is also checked automatically.
- **One diagnostic log line per lyrics lookup** — only in personal builds, in this device's `playback-diagnostics.log`. What is written is when · what called it (lookahead · panel · refresh) · the result kind · each request's response code · time taken, and, instead of the song, **the first 8 characters of the lyrics cache file name** (a hash of the song information) only. The title · artist · album are not written. Distribution builds do not write this log.
- **There is no YouTube Music app window now.** The window that opens YouTube Music inside the app cannot be turned on in any build, and the two places that window used, `music.youtube.com` · `accounts.google.com`, are also not in the table above — the app makes no requests there. YouTube Music is used through the Chrome · Edge extension: only song information and controls come over this Mac's socket, and the account stays in the browser as it is. If you signed in through that window before, delete the remaining web storage as in the "Web storage of the YouTube Music app window" row of the §2 table.

## 4. Permissions

| Permission | Why it is needed |
|---|---|
| Audio capture (`NSAudioCaptureUsageDescription`) | To receive system PCM and convert it to DSD. The Process Tap path |
| Audio input (`NSMicrophoneUsageDescription`) | When capturing the input device you chose (Fidenne Inlet, or a device picked under "+"). Only the device you chose |
| Apple Events (`NSAppleEventsUsageDescription`) | Showing the current song and controlling playback for Apple Music · Spotify |
| Apple Music library (`NSAppleMusicUsageDescription`) | Reading the whole library at once through MusicKit (library search · finding song links), and, for a played song (Apple Music · Spotify · YouTube Music), finding its other spelling and the same song in Apple Music (used only for lyrics lookup, matching the same song, and opening it in Apple Music; held in memory, never saved - only the link saying "these are the same song" is kept). If you do not allow it, the Music app is read through Apple Events and no other spelling is looked up |

The microphone permission is needed because macOS treats virtual audio **input devices** in the same category as microphones.
Fidenne reads only the selected input device and does not separately open the built-in microphone.
